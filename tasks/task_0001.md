# Interactive issue-worker conversations for Pi and Codex

Status: planned; implementation has not started.

Explored on: 2026-09-22. Repository baseline: `90e0bdf830436b3981b32a7017e1c18d41c7cdea`.

## 1. Objective

Let a human open the conversation of the agent that is actually executing a Multica issue, see its live output, send instructions into that same execution, and interrupt its current activity without cancelling the Multica run or restarting its process.

Initial supported providers are **Pi through its native RPC mode** and **Codex through its existing app-server integration**. Pi may be launched through the user's existing Nono wrapper. Steering or interrupting an open run must not relaunch that wrapper or create another sandbox.

This is a task for later implementation, not a description of functionality already present. Sections labeled “observed” describe the inspected source. Proposed types, endpoint names, tables, and state names are design recommendations, not existing APIs.

### Required user experience

1. An issue is assigned to an agent and Multica starts its ordinary issue run.
2. “Open conversation” opens the live transcript of **that worker**, not a different assistant answering questions about it.
3. Text, exposed reasoning, tool activity/results, and code-change events appear as the worker produces them.
4. A message sent while it works steers that worker using its native protocol.
5. Interrupt stops current agent activity, then leaves the run awaiting human input with the same process and provider conversation alive.
6. The human can think, type a corrective message, and continue in the same run.
7. Natural successful completion ends the Multica run and closes its process. Explicit Cancel run also closes it, with cancelled rather than completed status.
8. Opening a completed conversation only reads history. Sending a new message starts a new run/process that resumes the saved provider conversation when available.
9. An agent-assigned child issue gets this behavior through the same execution path as a human-assigned issue.

### Explicit scope boundaries

- One issue conversation, not one conversation shared across unrelated tasks.
- Multiple runs on the same issue can continue the saved provider history; they remain separate accounting/execution records.
- **No warm process pool after run completion. No 30-minute post-completion keepalive. No process reuse across completed runs.**
- Consequently, no cross-run live-process credential swap is required.
- A process remains alive after Interrupt only because its original run is still open.
- No Pi ACP dependency: native Pi RPC provides the needed transport.
- No rewrite of all agent backends, generic orchestrator, or replacement task system.
- No automatic attachment from Zed or simultaneous external writers to a provider session.
- No change to sandbox permissions, provider authentication policy, or approval policy as a side effect.
- No automatic support for native provider subagents as separate Multica chats. A delegated Multica child issue is a different concept.
- Web and desktop share this feature; mobile implementation is out of scope. API compatibility with existing clients remains required.

## 2. Terms and invariants

| Term | Meaning in this feature |
| --- | --- |
| Issue | The persistent board/task-management item. Its status is not an execution status. |
| Run | One `agent_task_queue` execution, including claim, credentials, usage, work directory, and terminal outcome. |
| Issue conversation | The UI/history identity for one issue, spanning its runs. |
| Provider session | Codex thread ID or Pi session JSONL path, owned by the corresponding provider/runtime context. |
| Activity | One submitted operation that can include many model responses/tool calls and native continuations. |
| Interrupt | Stop current activity and retain the live run/session for more input. |
| Cancel run | Terminally cancel the execution and release its process/resources. |

Do not use Pi `turn_end` as a synonym for the end of a Multica run. Pi calls one assistant response plus its tool calls/results a turn. Codex's protocol has different turn boundaries.

Hard invariants:

- Every displayed live event and accepted input is attributable to the same worker run and provider-session binding.
- One owner writes a provider session at a time. A browser tab is an observer/controller, never the process owner.
- Refreshing, opening a second tab, navigating away, or closing a window does not end a run or start a duplicate worker.
- Interrupt never calls the terminal cancellation path, revokes task credentials, finalizes the worktree, or closes the session result channel.
- A run produces exactly one terminal outcome and one final resource cleanup.
- Completion is determined from protocol outcome, not final-answer text, silence, or an issue being moved to Done.
- A recorded interrupt request is not proof that execution stopped.
- A late interrupt against an already completed activity is a harmless no-op. Do not reclassify completed work or add a special user-facing race-resolution flow.
- Messages accepted after a run is already terminal cannot be silently delivered into another run. The server returns the authoritative state and the UI offers/uses an explicit follow-up-run action.

## 3. Exploration: current implementation

These are source-level findings at the baseline above, not results of a real-agent execution test. Symbol names are more durable than line numbers.

### 3.1 Backend contract is one execution, one final result

Source: [agent.go](../server/pkg/agent/agent.go), `Backend`, `ExecOptions`, `Session`.

- `Backend.Execute(ctx, prompt, opts)` returns a `Session`.
- `Session.Messages` closes before `Session.Result` receives exactly one final result and closes.
- The session includes tool accounting and terminal-observation hooks used by watchdogs.
- `ExecOptions` already carries resume information, timeouts, model settings, and continuity-notice support.
- This is not presently a reusable conversation controller. Adding a send button alone cannot provide interactive issue sessions.

Preserve the existing contract for unsupported providers. Add an optional interactive capability rather than requiring every provider to implement steering. Do not emit a final `Result` on a nonterminal interruption.

### 3.2 Codex already uses app-server, but its execution lifecycle is bounded

Source: [codex.go](../server/pkg/agent/codex.go), `Execute`, `executeOnce`, `startOrResumeThread`, `interruptCodexTurn`, `handleRawNotification`.

- Launches `codex app-server --listen stdio://`.
- Starts/resumes a thread and starts a turn.
- Reads streamed notifications, including `turn/completed` with completion status and usage.
- Already has an interruption protocol followed by cleanup when the enclosing execution is cancelled.
- Existing execution orchestration and cleanup are single-execution oriented. The app-server transport alone does not mean Multica currently keeps it available for another turn in the same run.
- Reader state, terminal-observed state, final-answer buffers, turn IDs, usage, watchdog state, and completion signals must become activity-scoped where appropriate.

Reuse the existing transport/parser/approval handling. Avoid implementing a second Codex client. Verify `turn/steer`, `turn/interrupt`, and resumed-thread request schemas against the supported app-server version when implementing; do not infer exact wire shapes from method names.

### 3.3 Pi currently uses print/JSON mode

Source: [pi.go](../server/pkg/agent/pi.go), `Execute`, `buildPiArgs`, session locking, event parsing.

- Launches `pi -p --mode json --session <path>` with provider/model/runtime options.
- Supplies the prompt through stdin and closes it; source explicitly notes the EOF requirement for print mode.
- Parses JSON events for text, reasoning, tools, usage, and errors.
- Waits for process exit to settle execution.
- Uses persistent session files and an advisory session lock.

For interactive runs, switch the transport to `pi --mode rpc`, keep stdin open, and write RPC commands. Do not append RPC flags to the current print-mode argument builder: it deliberately owns/filters protocol arguments.

### 3.4 Pi protocol findings that affect correctness

Inspected installed Pi documentation/source at:

`/Users/abdou/.nvm/versions/node/v24.14.0/lib/node_modules/@earendil-works/pi-coding-agent/`

The inspection used the installed 0.87.0 package, especially `docs/rpc.md`, `dist/modes/rpc/rpc-mode.js`, and `dist/core/agent-session.js`. This absolute path is an exploration reference only, not an implementation dependency. Pin/document the actual supported protocol version and use checked-in fake-protocol fixtures in tests.

Observed semantics:

- `prompt` starts activity; a successful command response is not successful completion of that activity.
- `steer` and `follow_up` have distinct queueing semantics.
- `abort` waits for the session to become idle before returning success.
- `abort` may also be an idle no-op; its success alone does not prove it interrupted active work.
- `clear_queue` removes queued steering/follow-up text and returns it.
- The docs explicitly recommend `clear_queue` **before** `abort` for interactive Esc/Stop behavior. Otherwise queued messages can continue after abort.
- `agent_end` is a low-level end event; retries/compaction/queued continuation can still follow.
- `agent_settled` means the full session-level activity has settled, with no automatic continuation left.
- `agent_settled` does not itself carry an outcome/reason.
- Assistant messages expose `stopReason`, including `aborted` and `error`, but not every timing/operation should be assumed to produce a new aborted assistant message.

Therefore combine correlated control intent with the protocol's activity outcome and idle acknowledgement. Do not complete a run on `turn_end`, any arbitrary `agent_end`, or command acknowledgement.

### 3.5 Daemon owns execution, transcript draining, and teardown

Sources: [daemon.go](../server/internal/daemon/daemon.go), [client.go](../server/internal/daemon/client.go), [wakeup.go](../server/internal/daemon/wakeup.go).

Important symbols:

- `handleTask`: owns run context, cancellation polling, runner invocation, result reporting, and GC metadata.
- `watchTaskCancellation` / `shouldInterruptAgent`: stop work when the server task is terminal or deleted. They currently express terminal cancellation, not pause-for-input.
- `executeAndDrain`: starts the backend and drains messages before awaiting final result.
- `runIdleWatchdog`: enforces inactivity/tool budgets.
- `reportTaskResult`: maps final result into task completion/failure/cancellation reporting.
- `ReportTaskMessages`: sends worker transcript events to the backend.
- `readTaskWakeupMessagesForConnection`: existing daemon WebSocket receive path; control delivery needs integration and reconnect reconciliation here or its extracted equivalent.
- `gateResumeToReachableSession`: already considers provider-session reachability and execution-directory constraints.

`handleTask` creates a cancellable run context. Terminal task polling cancels it. Returning from the runner proceeds into usage reporting, worktree-related result handling, terminal reporting, and eventually GC metadata. An interrupt must stay inside the open runner/session loop rather than return through that terminal path.

### 3.6 Issue delegation already enters the task queue

Sources: [issue_trigger.go](../server/internal/service/issue_trigger.go), [task.go](../server/internal/service/task.go), [agent.sql](../server/pkg/db/queries/agent.sql).

- Issue trigger logic decides whether an assignment/comment should enqueue work; an assignment does not unconditionally start a process in every state.
- `EnqueueTaskForIssue`, `EnqueueTaskForIssueByActor`, `EnqueueTaskForIssueWithHandoff`, and `enqueueIssueTaskWithCommentPlan` are relevant entry points.
- Delegation lineage includes `delegatedFromTaskID`.
- `ClaimAgentTask` serializes active tasks using issue/agent or chat-session identity and existing active status lists.

Implement the capability in common issue execution, not only in a chat-screen launch handler. Preserve delegation, attribution, permissions, existing scheduling rules, and parent/child issue relationships.

### 3.7 Existing chat is not simply an issue conversation

Sources: [chat.sql](../server/pkg/db/queries/chat.sql), [chat.go](../server/internal/handler/chat.go), [chat_history.go](../server/internal/handler/chat_history.go), [use-chat-task-actions.ts](../packages/views/chat/components/use-chat-task-actions.ts).

- `CreateChatTask` explicitly inserts `issue_id = NULL` and a `chat_session_id`.
- Existing chat input is associated with newly queued tasks and has its own ownership, draft restoration, cancellation, and pending-task behavior.
- The existing chat Stop action calls task cancellation. Reusing that action unchanged violates this feature.
- Several code paths distinguish issue runs from chat runs. Do not set both IDs and assume all claim, authorization, completion, history, cleanup, and accounting branches support that shape.

Reuse rendering, batching, call IDs, output truncation, and transcript storage where possible. ### 3.9 Credentials have a real lifetime

Sources: [daemon handler](../server/internal/handler/daemon.go), [task service](../server/internal/service/task.go), [task_token.sql](../server/pkg/db/queries/task_token.sql), daemon runtime configuration.

- Task-scoped `mat_` credentials are minted with a 24-hour expiry in inspected claim paths.
- Token lookup checks expiry.
- Terminal completion/failure paths and cancellation revoke task tokens.
- Daemon runtime environment carries task/workspace/agent identity and task-scoped credentials.
- Codex receives task-specific runtime configuration, including a managed `CODEX_HOME` path in the execution path.

Keeping the same run open avoids cross-run credential replacement, but does not make its token immortal. Handle expiry explicitly; never substitute the owner's/daemon's broader credential to make an interrupted session work.

## 4. Recommended architecture

### 4.1 Keep scheduling and live conversation control separate

The server remains the authority for run ownership, authorization, durable input/control requests, and terminal state. The daemon owns the actual running process and serializes provider commands. The UI observes the server and sends requests through authenticated APIs.

Conceptual path:

`issue enqueue -> normal claim -> daemon run -> interactive backend -> actual provider session`

`issue conversation UI -> authenticated control/input API -> durable request -> owning daemon -> same interactive backend`

Provider output follows the existing task-message path back to persisted history and realtime subscribers. Browser WebSockets must never connect directly to provider stdin or hold task tokens.

### 4.2 Optional interactive backend capability

Keep the ordinary `Backend` execution path for unsupported providers and disabled mode. Add a narrow optional interface for opening a live execution/controller. Suggested responsibilities, not a mandatory Go signature:

- Open/start/resume using existing execution options, credentials, and runtime launch configuration.
- Stream normalized transcript and activity-state events.
- Submit input with explicit mode: start/resume-activity or steer.
- Interrupt the identified active activity without terminating the process.
- Expose observed idle/outcome state and native session identity.
- Close once at terminal run cleanup.

Capability metadata should distinguish live input, steering while busy, and interrupt-with-process-retention. A single `supports_chat` boolean is too vague. Initially advertise only capabilities actually implemented and protocol-version validated for Pi and Codex.

Do not over-generalize native protocol differences into dozens of speculative capabilities. Use typed commands/events and a small daemon-owned state machine. An interactive session can adapt its final terminal result back into existing run reporting, but nonterminal activity events must not close `Session.Messages`/`Result` or mark the run terminal.

### 4.3 One process lifetime per run

Start the provider once after claim. Keep the process, session lock, sandbox, task configuration, and execution context while working or awaiting input. Close only on run completion, failure, cancellation, explicit expiry, or daemon shutdown/loss handling.

Do not use `runCancel()` for Interrupt. Separate run lifetime cancellation from native activity interruption. Provider subprocess context must outlive the interrupted activity.

No process registry across finished runs is needed. The daemon needs only a registry of currently owned interactive runs, keyed by run ID plus an ownership/generation fence. Remove entries at cleanup.

### 4.4 Prefer an issue-conversation binding over changing chat-task identity

Recommended first implementation: retain issue runs as issue runs, introduce a canonical issue-conversation binding/history projection, and share chat transcript/composer components. Do not route active-run input through `CreateChatTask`.

The binding needs at least workspace/issue identity and a stable UI conversation ID. Provider-session binding also needs provider, agent/runtime identity, saved session locator, effective work directory, and continuity generation. Run IDs and activity IDs remain separate.

Reuse existing persisted session metadata when it already represents the correct binding; do not create a competing source of truth. Audit current resume lookup/writeback before selecting table fields.

One issue conversation is a UI identity, not a promise that incompatible runtimes share a provider session. If the user changes provider/agent/runtime such that the saved session cannot be resumed, retain the issue timeline and explicitly show a new provider-session segment. Never send a Pi path to Codex or silently pretend history was preserved. Initial interactive send should reject ambiguous ownership rather than select an arbitrary concurrently running worker.

For the initial supported path, enforce one controlling worker/session for the conversation. Existing claim serialization is not a universal cross-agent issue lock; inspect reassignment and concurrent-run cases and fence conversation ownership explicitly.

## 5. Lifecycle and completion policy

Use existing queue statuses for queue/claim/terminal lifecycle. Recommended: leave an interrupted open run in the existing nonterminal `running` lifecycle and add a separate interaction state, rather than introducing a new top-level queue status that every active-task query must immediately understand.

Suggested interaction states: `working`, `interrupting`, `awaiting_input`, `finishing`. Command delivery status is separate from run interaction state.

| Event | Run behavior | Process behavior |
| --- | --- | --- |
| Claim/start succeeds | Running, working | Start once |
| Human opens view | No execution transition | Unchanged |
| Send while working | Persist and deliver steer | Same process/session |
| Interrupt accepted by API | Pending request; not yet paused | Unchanged until native command |
| Runtime confirms interrupted/idle | Running, awaiting input | Retain process |
| Send while awaiting input | Running, working | New native activity, same process |
| Natural successful activity settles and no accepted input remains | Complete run | Flush, finalize, close |
| Runtime irrecoverable failure | Fail run | Flush and close |
| Explicit Cancel run | Cancel run using existing terminal semantics | Interrupt/terminate and close |
| User leaves view | No transition | Unchanged |
| Open completed history | Read only | No process |
| Send to completed conversation | Create new issue run resuming saved provider session | New process/Nono invocation |

Normal successful completion is still the default end of a run. This is not an always-open chat worker. Only successful human interruption intentionally leaves it awaiting corrective input.

When another input was durably accepted before finalization, do not drop it on natural completion. Serialize input acceptance and the transition to finishing. Either reserve/deliver it as another activity in the same run before finalization, or reject acceptance because the run was already closing. No silent accepted-but-lost message and no automatic duplicate follow-up run.

Marking the issue Done is not the completion signal. Preserve existing issue/run separation and documented explicit cancellation paths.

## 6. Interruption: use both intent and observed outcome

### Decision

Persist control intent on the server; use runtime acknowledgements and outcomes to determine what actually happened. This is stronger than either mechanism alone.

Runtime events distinguish many completion states, but they do not express whether Multica wanted a nonterminal Interrupt or a terminal Cancel run. Pi's settled event has no reason, and an abort acknowledgement can also be a no-op. Conversely, persisting “user pressed Interrupt” cannot prove a native operation stopped.

### Durable control record

Suggested fields:

- command ID / client idempotency key;
- workspace, run, and authorized actor;
- command kind (`interrupt`, and an integration reference for existing cancel semantics);
- expected ownership generation and active activity ID if known;
- created/delivered/acknowledged timestamps;
- outcome (`pending`, `applied`, `already_idle`, `rejected`, `failed`);
- structured error/reason without secrets.

Reuse existing durable delivery facilities if suitable; do not add a parallel cancellation authority. Cancel run should continue to use the established terminal transition and revocation path. An interrupt record is not permission to undo that transition.

### Delivery and acknowledgement

1. Validate membership, workspace, run control permission, active ownership, and capability.
2. Persist request idempotently before announcing delivery.
3. Notify the owning daemon; daemon reconnect reconciliation fetches pending requests.
4. Daemon serializes command handling for that run and confirms the targeted activity is still current.
5. Invoke the provider's native interrupt flow.
6. Observe native completion/idle; acknowledge the control outcome and update the interaction state.
7. If the activity had already completed normally, preserve success; acknowledge as already idle/no-op.

Keep a bounded in-memory deduplication/command state in the daemon, backed by durable server records. Never replay an old interrupt into the next activity. A transport failure after send but before acknowledgement creates uncertainty: reconcile current native state/activity identity; do not blindly repeat destructive commands against a newer activity.

UI shows “Interrupting” while pending and “Awaiting input” only after confirmation. On delivery failure, show retry/unavailable state. Do not optimistically claim the agent stopped.

### Pi-specific Stop behavior

- Serialize clear-queue, abort, and new input commands.
- Send `clear_queue`, retain returned messages with their input identities where possible, then `abort`.
- Reconcile returned queued inputs with persisted UI submissions and expose them as not-executed/restorable drafts; do not silently discard them or combine/reorder unrelated users' inputs.
- The abort response establishes idle; `agent_settled` and activity/message outcome establish what settled. Event ordering and no-message aborts need explicit tests.
- Cancel run can use the same native abort mechanism but always proceeds to terminal teardown.

### Codex-specific Stop behavior

- Target the actual thread/current turn, not a new resumed thread.
- Use `turn/interrupt` and correlated `turn/completed` outcome.
- Reset per-turn state before any subsequent `turn/start`; ignore stale prior-turn events.
- A naturally completed turn observed before the interrupt takes effect remains successful.
- Preserve existing bounded interruption and process-tree cleanup for terminal cancellation/shutdown; do not apply that cleanup to normal Interrupt.

## 7. Input, transcript, and history contract

### Input API

Define explicit operations rather than overloading issue comments or ordinary standalone chat sends:

- Get issue conversation, current owner/run, interaction state, capabilities, and paginated transcript.
- Submit input to an explicitly identified open run, with message ID/idempotency key and expected binding generation.
- Interrupt the current activity.
- Cancel run through existing cancellation semantics.
- Start a follow-up issue run for a completed conversation.

Final endpoint names should follow current route conventions. A follow-up run must use ordinary task authorization, attribution, enqueue, claim, and credential creation—not bypass them from the UI.

Every input has visible delivery state: pending, accepted/delivered, rejected, or uncertain. Persist the human message before delivery. Native protocol delivery is not a distributed exactly-once transaction; document how ambiguous sends are reconciled, and never promise exactly-once behavior that Pi/Codex cannot guarantee. Retry with the same ID must not unconditionally resend the prompt.

Distinguish input modes internally. While busy, default to native steering; while awaiting input, start the next activity. Do not silently turn a steer into a second independent queue task. If a runtime lacks the requested capability, report that clearly.

### Transcript events

Keep existing task-message storage as the source for worker output where practical. Add activity/run/session attribution needed to compose an issue-level history. Persist human inputs in one canonical location; reference them from transcript projection rather than dual-writing duplicate authoritative messages.

Include:

- human instructions and delivery state;
- assistant text and reasoning actually exposed by the provider;
- tool start, incremental updates where supported, results, errors, and file changes;
- interrupt/awaiting-input/resume and terminal markers;
- provider/session continuity notices;
- usage across all activities in the run.

Preserve event order, call IDs, sequence IDs, truncation markers, batching, and reconnect deduplication. Do not render a tool invocation and its result as unrelated text. “Full live output” means all relevant events exposed through the integration, not hidden model reasoning or an invented terminal stream the provider does not supply.

Final output may continue to appear in issue activity/comments through existing completion logic. Avoid posting every token as a comment or feeding the same message back into the worker through comment-trigger enqueue logic.

### Resume after terminal completion

- Save the provider locator and continuity metadata before terminal cleanup removes ephemeral configuration.
- Preserve existing reachable-session validation and work-directory constraints.
- New run gets new task-scoped credentials and process configuration while resuming the saved provider conversation.
- Recheck instruction/runtime configuration refresh on resumed sessions; saved history must not cause old task IDs/tokens to be reintroduced as live authority.
- If history is unavailable or incompatible, surface the continuity error/notice. Do not silently replace the session and claim it is the same history.
- Pi JSONL path must remain durable and readable through Nono. Its existing advisory lock protects Multica writers, not necessarily every external editor/client.
- Codex thread reachability must be verified with the actual per-task `CODEX_HOME`/session-home mechanism. Do not assume a saved thread ID alone suffices across configuration roots.

## 8. Resources, security, and failure handling

### Run ownership and resource accounting

An awaiting-input run remains open and owns its process, slot, session lock, worktree/environment, and task credentials. Initial implementation should retain its execution slot rather than releasing it while a live process still owns the work. Show awaiting-input distinctly so blocked capacity is understandable.

No final worktree delivery, commit/finalization, environment GC, delegated completion notification, or token revocation on Interrupt. Perform ordinary finalization exactly once when the run actually ends.

Keep wall-clock run duration truthful, including awaiting-input time. If active-compute time is added, it is a separate metric; do not rewrite existing elapsed-time semantics. Aggregate usage per activity without double-counting cumulative provider counters.

### Watchdogs and credentials

- Disable/suspend semantic inactivity and first-output watchdogs while confirmed awaiting input; human thinking is not an agent hang.
- Continue daemon/process liveness, ownership, and cancellation checks.
- Restore appropriate first-output/tool/activity budgets on resumed activity.
- Audit all outer run timeouts, stale-run reconciliation, task claims, active counts, leases, and GC guards. Changing only the inner watchdog is insufficient.
- Initial policy: retain the existing hard run/credential bounds; expose a finite pause/run deadline derived from the earliest applicable bound. Do not silently expire during a purportedly unlimited pause.
- On expiry, record a specific terminal reason, preserve history/work, and allow a new resumptive run. This is not normal Interrupt behavior.
- If product requirements later demand pauses beyond token lifetime, design same-run credential renewal separately with security review. It is not required to ship this feature and must not become a cross-run warm-pool project.

### Process and network failures

- Provider crash while awaiting input: fail the run visibly; do not keep a phantom “paused” controller.
- Browser disconnect: keep execution; reconnect uses server history/state.
- Server/daemon transport disconnect: bounded buffering and reconnect reconciliation; never grow memory unbounded or report unsent controls as applied.
- Daemon restart: do not claim the same process survived. Reconcile stale ownership, terminate/reap owned children where applicable, and use existing failure/recovery semantics. A later follow-up may resume persisted history in a new process.
- Explicit terminal cancellation while interrupt is pending: terminal cancellation wins; no subsequent input or acknowledgement can resurrect the run.
- Workspace/issue deletion or access revocation: preserve existing authorization/terminal cleanup behavior and remove newly added dependent records in application code.
- Multiple browser tabs: one shared server state; idempotent controls; no tab-local ownership claims.

### Sandbox and approval preservation

Launch through existing runtime executable/prefix/env configuration. A Nono wrapper must forward all Pi RPC args, keep stdin/stdout usable as protocol pipes, and avoid emitting non-JSON banners to stdout. Validate necessary Pi session/config/worktree/API access against the existing Nono profile without broadening it silently.

For Codex, retain the configured sandbox and approval handling. This task does not authorize YOLO mode or implement a new approval policy. If approval prompts need UI routing, reuse current supported handling; if unsupported, surface that limitation rather than auto-approve to keep the run moving.

Never expose task/provider secrets, credential files, full environment dumps, or raw managed auth configuration in transcripts or diagnostics.

## 9. Feature setting and compatibility

Add an opt-in “Interactive task sessions” setting at an existing suitable workspace/runtime configuration boundary. Prefer one setting with per-runtime capability reporting, not several overlapping toggles. Snapshot the effective mode at claim/start so toggling settings does not transform an already-running process.

- Enabled + supported Pi/Codex runtime: interactive execution.
- Disabled or other provider: current noninteractive execution and transcript behavior.
- Enabled but required protocol unsupported: fail validation/show unsupported capability; do not advertise interactive controls while silently running one-shot.
- Settings changes apply to new runs; a live interactive run can finish under its original mode.
- Older desktop clients must still be able to view tasks and use their existing explicit cancellation API. New interactive UI uses separate Interrupt; do not globally reinterpret old cancellation endpoints.

This explicitly requested retention of unsupported-provider behavior is not permission to add broad internal compatibility shims. Keep the optional capability boundary narrow.

## 12. Remaining implementation-time investigations

The design is decided; these are concrete code-integration questions, not requests to re-decide the product:

1. Which existing issue resume metadata can become the authoritative provider binding without duplication? Confirm writeback timing before cleanup and behavior on runtime/agent changes.
2. Where should durable control/input records integrate with existing WS reconciliation? Identify the current server-side runtime connection router and authorization middleware before adding endpoints.
3. Which outer timeout/lease paths can terminate an awaiting-input run? Derive the effective displayed hard deadline from actual configuration and token expiry rather than inventing an arbitrary timeout.
4. Does the configured Codex session-home mechanism guarantee saved-thread reachability across new runs? Test the actual managed-home path with fixtures; do not assume.
5. Which existing runner finalization defers must be held until terminal result? Trace worktree delivery and delegated recovery/notification paths fully before moving lifecycle boundaries.
6. Which Pi/Codex versions are supported in this fork? Establish minimum protocol capabilities and fixtures; avoid speculative compatibility fallbacks.
7. How should queued inputs cleared by Pi map to multi-user draft restoration? Preserve original authorship; never place another user's content silently into the current user's draft.
8. If the existing transcript schema cannot represent intermediate tool deltas or input delivery state, extend it deliberately with bounded payloads and ordering rules.

If any of these reveal that the proposed issue-conversation projection cannot reuse current storage safely, revise that narrow storage design before coding it. Do not change the central same-worker, interrupt-without-cancel, or no-cross-run-warm-process requirements.
